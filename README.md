# Terraform: multi-cluster vSphere deployment

Declarative deployment of multiple **vSphere compute clusters** (HA/DRS,
optionally **vSAN**), each with its own distributed switch, port groups, and
blank VMs built from scratch with an optional installer ISO.

Each cluster has **its own folder and its own Terraform state**. Every item is
configured in a small, human-readable JSON file. The actual Terraform logic
lives in one shared module, so you only maintain infrastructure code once.

## Provider note (important)

You selected `hashicorp/vsphere`. That namespace is **deprecated and frozen at
2.12.0** — VMware/Broadcom moved the provider to `vmware/vsphere`. This code
uses `vmware/vsphere ~> 2.13`, which is the same provider, actively maintained.
If you must stay on the old address, change `source` in both
`modules/vsphere-cluster/versions.tf` and `scripts/select-backend.ps1` to
`hashicorp/vsphere` and pin `version = "~> 2.12"`.

## Prerequisites

- Terraform >= 1.10
- vCenter Server (not direct ESXi — clusters, VDS and vSAN require vCenter)
- ESXi hosts already added to vCenter as **standalone** hosts
- Datastores for VMs and (optionally) ISO files
- A vCenter account with cluster, host, network and VM provisioning rights
- State storage in **either** Amazon S3 **or** Azure Blob Storage
- **For vSAN:** a vSAN license, a consistent disk layout on every host, and a
  VMkernel adapter with the vSAN service enabled on each host

## Quick start

```powershell
# 1. Shared settings (copy once, edit once)
Copy-Item globals.json.example globals.json
notepad globals.json

# 2. Pick a state backend: AWS S3 or AzureRM
Copy-Item backend\aws.hcl.example backend\aws.hcl     # or azure.hcl.example
notepad backend\aws.hcl
powershell -ExecutionPolicy Bypass -File .\scripts\select-backend.ps1 -Cloud aws
#   OR: ... -Cloud azure

# 3. Edit each cluster's JSON files
notepad clusters\CLUSTER-PROD-01\cluster.json

# 4. The password is never stored in a file
$env:TF_VAR_vsphere_password = "your-vcenter-password"

# 5. Initialise, validate and apply each cluster independently
cd clusters\CLUSTER-PROD-01
terraform init -backend-config=backend.hcl
terraform fmt -check -recursive
terraform validate
terraform plan -out=tfplan
terraform apply tfplan
```

Repeat step 5 for `CLUSTER-DEV-01` (or any other cluster folder). Clusters are
fully independent: a failure in one never blocks another.

## Selecting the state backend

The backend **type** is part of Terraform configuration, so it cannot be
switched by `-backend-config` alone. `scripts/select-backend.ps1` generates a
small `backend.tf` (with the chosen type) and a `backend.hcl` (with the shared
values plus a unique state key) in **every** cluster folder.

```powershell
# Amazon S3
Copy-Item backend\aws.hcl.example backend\aws.hcl
powershell -ExecutionPolicy Bypass -File .\scripts\select-backend.ps1 -Cloud aws

# AzureRM
Copy-Item backend\azure.hcl.example backend\azure.hcl
powershell -ExecutionPolicy Bypass -File .\scripts\select-backend.ps1 -Cloud azure -KeyPrefix tfstate
```

Keys are generated automatically:

| Cloud | Example key |
|---|---|
| AWS S3 | `vsphere/CLUSTER-PROD-01/terraform.tfstate` |
| AzureRM | `tfstate/CLUSTER-PROD-01.tfstate` |

Do not put a `key` in the shared `backend/*.hcl` file — the script adds it.
After switching backend type, run `terraform init -reconfigure
-backend-config=backend.hcl` in each cluster folder so Terraform can migrate
state. `-ExecutionPolicy Bypass` is only needed if your machine blocks local
scripts; you can also run `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

## The JSON configuration files

### `cluster.json` — one per cluster

Holds the cluster name, HA/DRS/EVC settings, the ESXi host list, vSAN settings
and the VDS configuration:

```json
{
  "name": "CLUSTER-PROD-01",
  "folder": "Compute",
  "drs_enabled": true,
  "drs_automation_level": "fullyAutomated",
  "ha_enabled": true,
  "evc_mode": "intel-skylake",
  "esxi_hosts": [
    "esxi-01.example.local",
    "esxi-02.example.local",
    "esxi-03.example.local"
  ],
  "vsan": { "enabled": true },
  "create_networks": true,
  "vds": {
    "name": "VDS-PROD-01",
    "uplinks": ["uplink1", "uplink2"],
    "active_uplinks": ["uplink1", "uplink2"],
    "host_uplinks": {
      "esxi-01.example.local": ["vmnic0", "vmnic1"]
    }
  },
  "existing_networks": {}
}
```

All keys are optional except `name`. The files in the repo are complete
examples — copy and edit rather than writing from scratch.

### `networks/<NAME>.json` — one file per port group

The **file name** is the logical network name that machines refer to:

```json
{
  "vlan_id": 200,
  "type": "earlyBinding",
  "description": "Application traffic"
}
```

To reuse networks that already exist in vCenter, set `"create_networks": false`
in `cluster.json`, then map every file name to a vCenter name in
`existing_networks`.

### `machines/<NAME>.json` — one file per VM

The file name must match the `name` field. Select an OS with `os`, `version`
and optional `variant`; the template, guest ID and default disk size come from
[`images/catalog.json`](images/README.md):

```json
{
  "name": "prod-app-01",
  "num_cpus": 4,
  "memory": 8192,
  "os": "ubuntu",
  "version": "24.04",
  "variant": "default",
  "thin_provisioned": true,
  "networks": ["NET-DATA"],
  "annotation": "Application node - Terraform managed"
}
```

Supported values: `centos`, `rockylinux`, `almalinux`, `ubuntu`, `debian` and
`windows`. Omitted `variant` means `default`. `disk_size`, `guest_id` and
`template_name` can be overridden per machine.

Optional guest customisation: `hostname` (defaults to `name`), `domain`
(defaults to `local`), `ipv4_address`, `ipv4_netmask`, `ipv4_gateway`,
`dns_server_list` and `dns_suffix_list`. A static address is applied to the
first network in `networks`; the rest use DHCP. Windows clones additionally
require `TF_VAR_windows_admin_password` for sysprep.

A machine **without** `os` keeps the original blank-VM behaviour. In that case
`guest_id` and `disk_size` are required, and `iso_path` is relative to the root
of `iso_datastore_name` — do **not** use `[datastore] path` notation. Set
`"iso_path": null` for a diskless-boot or PXE VM.

## Optional first-boot Ansible bootstrap

Every VM can optionally install **ansible-core** and run **ansible-pull** once on
first boot. It is off by default. Configure defaults once in `cluster.json`, then
override or disable them per machine in `machines/<NAME>.json`:

```json
// cluster.json
"ansible": {
  "enabled": true,
  "repository": "https://github.com/example/ansible-playbooks.git",
  "playbook": "site.yml",
  "branch": "main",
  "package_name": "ansible-core",
  "install_packages": true,
  "run_pull": true,
  "extra_vars": { "environment": "prod" }
}
```

```json
// machines/prod-app-01.json
"ansible": {
  "enabled": true,
  "playbook": "app.yml"
}
```

Any field left out of a machine's `ansible` object inherits the cluster value.
`"enabled": false` on a machine disables it even when the cluster enables it.
Omitting `ansible` entirely also inherits the cluster setting.

| Field | Default | Purpose |
|---|---|---|
| `enabled` | `false` | Enable/disable the bootstrap. |
| `repository` | none | Git URL passed to `ansible-pull -U`. Required when enabled. |
| `playbook` | `site.yml` | Playbook path inside the repository. |
| `branch` | `main` | Git branch to pull. |
| `directory` | `/opt/ansible-pull` or `C:\ansible-pull` | Working directory for the checkout. |
| `requirements_file` | none | Optional Galaxy requirements file (`-r`). |
| `extra_vars` | `{}` | Extra variables written to a JSON file and passed with `-e @file`. |
| `package_name` | `ansible-core` | Package/pip name to install. |
| `install_packages` | `true` | Install git, Python and `package_name` first. |
| `run_pull` | `true` | Run `ansible-pull` after installing (set `false` to install only). |

What Terraform generates:

- **Cloned Linux VMs:** the bootstrap is injected into
  `clone.customize.linux_options.script_text` and runs on first boot.
- **Cloned Windows VMs:** the bootstrap is wrapped into a Sysprep
  `run_once_command_list` command and runs once as local SYSTEM. Python must be
  present on the template, or set `install_packages: false` when ansible-core is
  already installed.
- **Blank VMs (no `os`):** there is no guest customization to hook, so the
  configuration and both bootstrap scripts are staged as base64 `guestinfo.*`
  values on the VM. A guest with cloud-init/cloudbase-init can consume them, or
  you can run the staged Linux/Windows script manually after installing the OS.

Logs go to `/var/log/ansible-first-boot.log` (Linux) or
`%TEMP%\ansible-first-boot.log` (Windows). The scripts are generated from
[`modules/vsphere-cluster/templates/`](modules/vsphere-cluster/templates/) and
need no extra pipeline or host-side download.

## OS images and VM provisioning

Linux images come from <https://www.linuxvmimages.com/images/vmware/>. The site
publishes complete VMware VMs as 7z archives (VMX + VMDK) with MD5 and SHA-1
checksums. `scripts/prepare-vm-images.ps1` automates the whole workflow:

1. download the archive referenced by the selected catalog entry,
2. verify the published MD5 and SHA-1 and cache a locally computed SHA-256,
3. extract the VM and upload it to the template folder on the datastore,
4. register it as a vCenter template with `govc vm.register -template`, and
5. skip the image entirely if that template already exists (idempotent).

Terraform then clones the template with `clone { customize { ... } }`. Firmware,
SCSI controller and hardware version are inherited from the template. Run the
**Images** pipeline once before Plan/Create for a cluster that uses OS
selection, otherwise the template data source cannot resolve.

Windows images are not downloadable from that site. Maintain a sysprepped
Windows template in vCenter with the name from the catalog (for example
`TEMPLATE-WINDOWS-2022-STANDARD`); the Images pipeline verifies that it exists.

See [`images/README.md`](images/README.md) for the full catalog format,
supported versions and how to add an image.

## vSAN configuration

vSAN is configured in the `vsan` object of each cluster's `cluster.json`. With
`"enabled": false` (the DEV example), no vSAN settings are sent to vSphere.

### Original Storage Architecture (OSA)

```json
"vsan": {
  "enabled": true,
  "esa_enabled": false,
  "unmap_enabled": false,
  "dedup_enabled": true,
  "compression_enabled": true,
  "performance_enabled": true,
  "dit_encryption_enabled": false,
  "dit_rekey_interval": 1440,
  "remote_datastore_ids": [],
  "disk_groups": [
    {
      "cache": "naa.REPLACE_WITH_CACHE_DISK_ID",
      "storage": [
        "naa.REPLACE_WITH_CAPACITY_DISK_1_ID",
        "naa.REPLACE_WITH_CAPACITY_DISK_2_ID"
      ]
    }
  ],
  "fault_domains": {
    "RACK-1": ["esxi-01.example.local", "esxi-02.example.local"],
    "RACK-2": ["esxi-03.example.local"]
  }
}
```

### Express Storage Architecture (ESA) — vSphere 8+

ESA uses NVMe/TLC devices and **cannot** be combined with deduplication or
compression. UNMAP is mandatory:

```json
"vsan": {
  "enabled": true,
  "esa_enabled": true,
  "unmap_enabled": true,
  "dedup_enabled": false,
  "compression_enabled": false,
  "disk_groups": [
    {
      "cache": "naa.REPLACE_WITH_CACHE_DISK_ID",
      "storage": ["naa.REPLACE_WITH_CAPACITY_DISK_1_ID"]
    }
  ],
  "fault_domains": {}
}
```

### Disk-group semantics (important)

Disk groups use **canonical disk names** (`naa.*` / `eui.*` / `mpx.*`), not
device labels. Find them with:

```powershell
Get-VMHost esxi-01 | Get-PhysicalDisk | Select-Object CanonicalName, DeviceType, IsSSD
```

The `vmware/vsphere` provider has **no host field** on `vsan_disk_group`: it
applies each entry to **every host in that cluster with the matching disks**.
Use an identical disk layout on all hosts in a vSAN cluster, and replace all
`naa.REPLACE_WITH_*` placeholders before applying.

### Fault domains, stretched clusters, encryption

- `fault_domains` maps a domain name to host inventory names. Every host must
  also be in `esxi_hosts`. Mutually exclusive with `stretched_cluster`.
- A stretched cluster is enabled by setting `stretched_cluster.witness_host` to
  an existing host/witness appliance, plus `preferred_hosts` and
  `secondary_hosts` from `esxi_hosts`.
- `dit_rekey_interval` is in minutes (30–10080). DIT encryption conflicts with
  HCI Mesh `remote_datastore_ids` (max 5).

### vSAN + HA ordering caveat

The provider applies vSAN settings **before** HA, so both normally work in one
apply. If your vCenter rejects HA while vSAN is still initialising, apply once
with `"ha_enabled": false`, wait for the vSAN datastore, then set it to `true`.

Host VMkernel adapters are **out of scope** (like the hosts themselves). Before
enabling vSAN, attach a VMkernel adapter with the vSAN service to each host —
the `NET-VSAN` port group is already defined in the PROD example.

## Adding another cluster

1. Copy an existing cluster folder:
   ```powershell
   Copy-Item clusters\CLUSTER-DEV-01 clusters\CLUSTER-QA-01 -Recurse
   ```
2. Delete its `.terraform/` and `.terraform.lock.hcl` (if present).
3. Edit `cluster.json`, the `networks/*.json`, `machines/*.json` and
   `imports/*.json` files (the latter hold real vCenter paths for adoption).
4. Run `select-backend.ps1` again — it will generate a fresh `backend.tf` and a
   unique state key for the new folder.
5. `cd clusters\CLUSTER-QA-01`, then `terraform init -backend-config=backend.hcl`
   and `terraform apply`.

No edits to the shared module are needed.

## Design decisions and safety notes

- **One state per cluster.** Each folder is an independent root module, so a
  broken apply or state lock is contained to one cluster.
- **JSON as the source of truth.** Terraform reads the JSON files on every
  plan. Adding/removing a JSON file adds/removes that item without code changes.
- **Machines without an OS stay blank.** They are created with a VMDK and
  optional ISO, are not powered on, and have the guest waiters disabled. The
  optional first-boot Ansible bootstrap is staged in `guestinfo.*` for them.
- **Hosts are not created.** ESXi hosts must already exist in vCenter. Removing
  a host from `cluster.json` puts it into maintenance mode — remove hosts one
  at a time.
- **vSAN claims disks.** Confirm the `naa.*` IDs before applying; disks in a
  disk group are formatted.
- **Secrets stay out of Git.** `globals.json`, `backend/*.hcl`, per-cluster
  `backend.tf`/`backend.hcl` and `*.tfstate` are ignored. Use
  `TF_VAR_vsphere_password`.
- **Validation is built in.** Bad VLANs, unknown network references, wrong
  uplink counts, invalid vSAN combinations and machine file-name mismatches
  fail at `plan` time.

## Adopting existing infrastructure

The real vCenter object paths live in `clusters/<CLUSTER>/imports/`, separate
from the desired-state config. Each cluster has three files:

| File | Contents |
|---|---|
| `imports/cluster.json` | Cluster inventory path (vSAN is adopted with it) |
| `imports/networks.json` | VDS path plus one entry per port group |
| `imports/machines.json` | One entry per VM |

```json
{
  "resource": "vsphere_compute_cluster.this",
  "path": "/{datacenter}/host/Compute/CLUSTER-PROD-01"
}
```

`{datacenter}` is substituted from `DATACENTER_NAME`. Use a literal path for VMs
inside folders, e.g. `/DC01/vm/Production/prod-app-01`.

The **import pipeline** (see [`azure-pipelines/README.md`](azure-pipelines/README.md)) reads
these files, skips addresses already in state, warns on bad paths, and prints a
post-import plan. Start with `dryRun: true` to verify the paths.

To import manually instead, run the equivalent commands in the cluster folder:

```powershell
terraform import vsphere_compute_cluster.this /DC01/host/Compute/CLUSTER-PROD-01
terraform import 'vsphere_distributed_virtual_switch.this[0]' /DC01/network/VDS-PROD-01
terraform import 'vsphere_distributed_port_group.this["NET-DATA"]' /DC01/network/NET-DATA
terraform import 'vsphere_virtual_machine.machine["prod-app-01"]' /DC01/vm/prod-app-01
```

vSAN is configured on the cluster resource, so disk groups, fault domains,
stretched cluster and DIT encryption are imported with it. After importing, run
`terraform plan` and reconcile drift before applying.

## CI/CD pipelines

Two equivalent sets of six pipelines are provided:

- **Azure DevOps** — [`azure-pipelines/`](azure-pipelines/README.md): Create
  (apply), Delete (destroy), Plan, Drift detection, Import and Images (OS template
  preparation). The Terraform pipelines share `templates/terraform-init.yml`,
  use the `terraform-backend` variable group, and take `clusterName` and `cloud`
  (`aws` | `azure`) parameters.
- **GitHub Actions** — [`github-actions/`](github-actions/README.md): the same
  six workflows, using a shared composite action plus repository variables
  and secrets.

Both sets read the same cluster JSON files and `imports/*.json` paths. Edit the
GitHub sources in `github-actions/`, then run
`powershell -ExecutionPolicy Bypass -File .\scripts\sync-github-workflows.ps1`
to mirror them into `.github/workflows/` and `.github/actions/`, which are the
only locations GitHub reads.

## Useful commands

Run these from inside a cluster folder:

```powershell
terraform plan -refresh-only          # detect out-of-band vSphere changes
terraform output -json                # cluster, network, vSAN and machine IDs
terraform state list                  # everything currently managed
```
